# Alpha 早期公測決策(#157)

- 日期:2026-10-27 評估;2026-10-28 作者決定
- 狀態:**作者已決定**(見「作者決定」)。本文件是評估與決定紀錄;評估階段不建立 release、tag 或 CI workflow。
- 與會:Codex(Issue 指定主導)、DeepSeek(Pi)、Max(Claude Code,主持與彙整)。開了兩輪:各自獨立評估,再交換報告互評。

## 一句話結論

**現在先不宣布 Alpha。** 先花約 2–3 個工作日補齊「發佈準備」,再加上作者 1–2 小時的實際寫作驗收,通過後就以 **Windows 免安裝 ZIP、公開放在 GitHub Release、任何人都能下載** 的方式開始 Alpha。

**這是公開測試,不是封閉測試**:不邀請、不審核、不限人數,沒有任何報名手續。

程式本身的基礎已經夠用:Go 測試、`go vet`、前端型別檢查都通過,三條硬線(未經作者接受不改稿、改了能復原、未確認不送雲端)都有既有測試支持。缺的是發佈相關的準備,以及在別人電腦上實際跑一次的證據。

## 作者決定(2026-10-28)

1. **公開測試,不是封閉測試**。照下方門檻準備好就開放,不邀請特定測試者。
2. **版本號**:第一版 `0.1.0-a1`。
   - 小修補進第三位:`0.1.0-a1` → `0.1.1-a1`(作者舉例 `0.1.5-a1` 即第五次小修補)。
   - 大修補、功能改進或新增功能進第二位:`0.2.0-a1`。
   - `-a1` 是 Alpha 階段標記,整個 Alpha 期間固定不變,版本只靠前面的數字區分;進入 Beta 再換字樣。
   - 因此 `app/wails.json` 的 `productVersion` 改回 `0.1.0`,SPEC §「應用程式顯示名稱」裡「`0.2.0` 對應第二階段規格」的說法一併改掉,由必做第 2 項處理。
3. **分發**:直接放公開的 GitHub Release(標成預發行版本),任何人都能下載,不需要邀請手續。
4. **回報**:一律在 GitHub Issue 回報,不另設私下管道。限制:**Issue 若是 AI 寫的,必須註明**。
   - 作者的理由:這是離線的文字編輯器加上 agent harness,沒有伺服器;API 金鑰存在使用者自己電腦的 Windows 認證管理員,沒有特別需要私下處理的安全問題。
   - Orchestrator 同意:沒有伺服器,就沒有「公開細節會讓別人被攻擊」的漏洞類型;即使出現「未確認就送出稿件」這類違反硬線的 bug,公開回報也不會讓第三方利用它。真正要防的是**測試者自己在公開 Issue 貼出金鑰或稿件**,這由公測說明與 Issue 表單的提醒處理(必做第 3、4 項)。
5. **支援範圍**:市面上絕大多數大型語言模型都支援,但**不保證 agent 的輔助效果**;目前只驗證過**注音輸入法**可以正常輸入,其他輸入法待驗證。Windows 版本作者未指定;Orchestrator 的技術預設為 Windows 10/11 64 位元(建置目標為 amd64,且需要 WebView2),作者可推翻。
6. **Alpha 期間的工作方針**:沿用目前「克制改善、Bot 穩定性優先」的方針,不另外宣布功能凍結或固定發版週期。
7. **第一輪的成功條件**:沒有未解決的稿件遺失或未經同意的外送,回報的嚴重問題都有處置。不設人數或 Bug 數量目標。

## 兩方的共識

- **門檻不是「待辦清空」**,而是三件事:三條硬線守得住、別人的電腦能正常開起來、出問題能回報與追查。
- **第一版只發 Windows 免安裝 ZIP**(執行檔 + 說明 + 授權 + 檢查碼)。不做安裝檔、自動更新、程式簽章、多平台。
- **CI 只放基本檢查,E2E 先不上 CI**。現行 E2E 在本機要開 `wails dev` 的視窗、會讀寫作者的設定檔、寫死 Edge 的路徑(`app/e2e/lib.js`),測試組之間也有先後依賴,現在搬上 CI 不划算(GitHub 主機能不能跑 `wails dev` 未實測)。
- **發佈檔一律從指定的 main 提交重新建置**。不使用現有的 `app/build/bin/perkins.exe`,它是 10/25 建的,已經落後 main。
- **不另開 CHANGELOG 檔**。Release 說明直接從 `docs/PROGRESS.md` 整理成使用者看得懂的文字,並寫上設定搬移等相容性事項。
- **可以延後的**:#28 / #158 介面打磨、#154 提示詞研究、#115 長期記憶、#41、#29、E2E 上 CI、程式內「回報問題」按鈕。**#161(表格顯示不正常)有條件延後**:先確認只是顯示問題、不影響編輯與存檔,才可延後;若影響編輯或存檔就列為阻擋。(DeepSeek 認為 Issue 內文已定位在 Bot 回覆的顯示;Codex 認為標題指向稿紙化、發生位置仍待確認,不能就此定案。)
- **測試綠燈不等於安全審計**。DeepSeek 做過有限的搜尋(常見金鑰樣式、歷史提交裡有沒有加入過敏感檔名),沒有命中;Codex 核對了相關的程式邊界與測試,沒有做金鑰或歷史掃描。雙方同意這只能說明「沒找到」,不能說成「已確認安全」。

## 兩方的分歧與結果

1. **版本號叫 `v0.2.0-alpha.1` 還是 `v0.3.0-alpha.1`?**
   - Codex 主張 0.2.0:SPEC 裡 0.2.0 對應的是第二階段規格,沒必要為了公測升一版。
   - DeepSeek 主張 0.3.0:這一輪有使用者看得到的改動,而且 Windows 執行檔的版本欄位會顯示 `0.3.0`,跟 tag 名字比較對得上。
   - **作者決定:兩者都不用**,改從 `0.1.0-a1` 起算(見作者決定第 2 點)。DeepSeek 擔心的「名稱對不上」由必做第 2 項的程式內完整版本處理。
2. **公開 Release 還是私下傳連結?**
   - DeepSeek 傾向不公告、只私下給測試者連結。Codex 建議公開的預發行版,並提醒公開倉庫的 Release 即使只私下給連結,任何人仍抓得到。
   - **作者決定:公開 Release、任何人都能下載,不是封閉測試**。
3. **「已經達到 Alpha 條件」可以講多肯定?**
   - DeepSeek 第一輪說「程式本身已經夠格」,Codex 認為證據不夠。雙方第二輪收斂成:**程式層的證據足以準備候選版本,但要通過乾淨電腦實測和作者實際寫作驗收(必做第 6、7 項),才算可以開放。**
4. **Alpha 期間要不要凍結新功能?**
   - DeepSeek 主張凍結到 Alpha 結束;Codex 主張沿用目前的克制方針,不另外宣布凍結。
   - **作者決定:沿用目前方針,不另外宣布凍結。**
