# Perkins Bot 實機評測(SPEC §16 第 22 項)

固定情境的實機評測,用來比較不同版本(模型、系統提示、工具流程、上下文組裝)的表現,避免功能變強但寫作品味變差。程式在 `app/internal/agent/live_eval_test.go`,情境是一組為評測撰寫的小型虛構作品(海邊小鎮),不使用作者稿件。

## 怎麼執行

需要本機 LM Studio(`http://localhost:1234/v1`)已載入模型,平常不執行(未設環境變數時全部 skip):

```
PERKINS_LIVE_MODEL=<模型id> go test ./internal/agent -run TestLiveEvalCases -v -timeout 30m
```

要把結果寫成報告檔(方便比較不同版本),再加 `PERKINS_EVAL_OUT`:

```
PERKINS_LIVE_MODEL=<模型id> PERKINS_EVAL_OUT=報告.md go test ./internal/agent -run TestLiveEvalCases -v -timeout 30m
```

Windows PowerShell:`$env:PERKINS_LIVE_MODEL="模型id"; $env:PERKINS_EVAL_OUT="報告.md"; go test ./internal/agent -run TestLiveEvalCases -v -timeout 30m`

- `-run TestLiveEvalCases` 只跑評測情境;`-run Live` 會連同 `live_test.go` 的兩個舊實機測試一起跑。
- 本機模型跑一輪約 5–6 分鐘;注意記憶體,一次跑一輪即可。
- 純判定邏輯的單元測試(`TestEvalJudge*`,不寫任何檔案)隨一般 `go test ./internal/agent` 預設執行。
- 另有一個用假 LLM 走完整 Ask 流程的檔案整合測試(`TestEvalJudgeWithScriptedLLM`),只寫進 Go 測試的 `t.TempDir()`(測試結束自動清除),以 `PERKINS_EVAL_INTEGRATION=1` 選用執行。

## 何時該跑

- 大改系統提示(`agent.go` 的 `systemPrompt`);
- 改工具流程(白名單、`runTool`、提案建立);
- 改上下文組裝(`BuildMessages`、壓縮、前情摘要);
- 換模型或端點,想比較表現時。

## 情境與判定

硬判定(不通過代表護欄或工具流程有問題)只有三類,都是程式可確定的:

| 檢查 | 說明 |
|---|---|
| 檔案未被改動 | 每個情境結束比對檔案快照:AI 不得未經提案改動任何檔案(G1/G2) |
| 指定文件有提案 | 需要提案的情境,必須對指定文件有提案;只改到附件設定等其他檔案不算 |
| 提案原文逐字複製 | 依各提案「實際的目標檔」驗證原文逐字存在(含目標檔讀不到的情況,視為不合格) |

| 情境 | 硬判定 | 人工檢查 |
|---|---|---|
| 角色口吻 | 三項硬判定 | 改寫是否貼合設定中的說話方式 |
| 設定衝突 | 三項硬判定 | 回覆是否指出與 Canon 的矛盾(而非默默照改) |
| 伏筆不可擅自補完 | 三項硬判定 | 改寫有沒有把伏筆寫進正文(見下方字串提示) |
| 改寫不改變敘事意圖 | 三項硬判定 | 視角、動作主體、時間順序是否未變(見下方字串提示) |
| 提案原文逐字複製 | 三項硬判定 | — |
| 報告模式不提案 | 不建立任何提案 + 三項硬判定 | 報告有無依據、推測有無標示 |

**字串提示(不影響判定)**:伏筆情境掃描「女兒」「失蹤」「遺物」,敘事意圖情境掃描「小嵐」「我把」「我走進」。字串無法對應語意——例如「羅盤宛如舊時代的遺物」是比喻、沒有洩漏,「羅盤裡刻著他失聯孩子的姓名」換了說法卻真的洩漏;所以這些字串只作為提示記錄在報告(「字串提示」列),供人工檢索,**未出現不代表沒有洩漏、也不能證明意圖未變**,一律以人工檢查為準。

## 怎麼看報告

報告(Markdown)每個情境一節:✅/❌ 總判定(只由硬判定決定)、逐項程式檢查、字串提示、工具呼叫、提案(原文/改寫/理由/假設)、完整回覆、人工比對項目。

- **程式判定**通過/不通過是硬標準:不通過代表護欄或工具流程有問題,應修程式或提示。
- **字串提示**與**人工比對**是品味與語意標準:同一情境在不同版本間比較回覆與提案文字,挑選寫作上更好的版本。判定以程式可確定的條件為主,主觀項目不寫成會隨機失敗的斷言。
