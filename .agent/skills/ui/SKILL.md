# 介面任務工作流

## 何時使用

新增或修改任何畫面、元件、版型、文案或轉場時。純 Go 邏輯、不影響畫面的前端修改不必使用。規則本身以 `docs/UI_GUIDE.md` 為準,本技能只寫操作步驟。

## 步驟

1. **讀依據**:SPEC 相關章節、`docs/UI_GUIDE.md` 相關條款、要改的元件與 `components/ui/` 現有元件。條款與現有程式不一致時,依 UI_GUIDE §0 先問作者,不自行擇一。
2. **寫狀態清單**(放在任務說明或 PR 內文):
   - 對應條款、要改的畫面、可重用元件。
   - 狀態:空、載入中、成功、錯誤、超長文字、停用(附原因);Bot 相關加工具成功/錯誤/被拒、提案衝突。只列這次改動會碰到的。
   - 從 UI_GUIDE §13 驗收矩陣挑出要看的組合。
3. **判斷是否需要設計預覽**(UI_GUIDE §16 第 2 步的三個觸發條件)。需要時:
   - 在任務工作樹先做只有畫面的版本,假資料以開發模式才存在的方式注入(現有做法是 `import.meta.env.DEV` 下的 `window.__perkins*` 鉤子,例如 `__perkinsChatInject`);不呼叫模型、不改 Go。
   - 截圖(1280 與 640、深淺主題)加差異摘要,交 Orchestrator 轉給作者;有多個方案時每案各一組截圖,可附推薦與理由,由作者決定。
   - 作者確認前不接功能、不送審。作者否決或修改時,在同一預覽上改,不重開一套。
4. **整合**:接真實綁定;失敗要顯示在發生處(UI_GUIDE §6)。確認沒有把預覽用的假資料留在正式資料流程;開發鉤子只能在 `import.meta.env.DEV` 下存在,建置後 grep `app/frontend/dist` 確認不含新加的鉤子名稱。
5. **驗收**:
   - `cd app/frontend && npm run build`(含 `tsc`)。
   - 實際 render:必看項(深淺主題、640 與 1280、設定頁加 900)+ 步驟 2 挑的組合。截圖要親自看過;看不到圖的環境(例如無法 render 的雲端環境)寫「未檢視」,不推測畫面。
   - 互動與護欄依 `.agent/skills/e2e/SKILL.md`「何時跑哪些組」選組。
6. **交付報告**(回報與 PR 內文用):

```
## 介面
- 範圍與條款:<SPEC §…、UI_GUIDE §…>
- 設計預覽:<不需要(理由)/作者已確認(出處)>
- 已檢查:<狀態 × 組合>,截圖:<路徑>,由 <角色> 檢視
- 未檢查:<狀態或組合,沒有就寫「無」>
## 驗證
- 建置:<npm run build 結果>
- E2E:<組名 通過數/總數,或「未執行」與原因>
```

## 限制

- 不為了預覽新增依賴;Gallery 與截圖腳本(#198)作者決定前不自行建立。
- 預覽與驗收照 AGENTS.md「驗證保持克制」:只看這次改動的風險點,不把矩陣每一格都拍。
- 主審若只看 diff 文字,報告中寫明視覺由誰看過;高風險 UI(提案審核、Canon 寫入)的子代理審查附上截圖路徑。
